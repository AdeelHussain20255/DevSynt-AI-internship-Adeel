Day 1: What is LangChain?

Chains vs. Raw API Calls

What is a Chain?

A chain is a fixed, step-by-step pipeline where data flows in a straight line from start to finish. Instead of calling an LLM API directly every time, LangChain gives you reusable building blocks.

Without LangChain (Raw API): 
prompt = "Explain what is a chain"
response = llm.call(prompt)
# You write the full prompt every time
# Raw text back - hard to parse
With LangChain (Chain): 
chain = prompt_template | llm | output_parser
result = chain.invoke({"topic": "chains"})
# Reusable, structured, reliable

Key Concepts

  • LLM Wrapper: A clean interface to any LLM (GPT, Gemini, Groq)
  • Prompt Template: A reusable prompt with {variables} you fill in
  • Chain: Connected components (template → LLM → parser)
  • LCEL: LangChain Expression Language - uses | to connect pieces

The 5-Step Chain Pipeline

Chain vs. Raw API Calls

Aspect Raw API Call LangChain Chain
Reusability Write prompt every time Template reusable
Output Structure Free-flowing text Structured (JSON/Pydantic)
Switching LLMs Rewrite entire code Change one line
Speed Fast, single step Slightly slower (structured)
Flexibility Fixed behavior Fixed behavior (predictable)
Key Takeaway: Chains are predictable, reusable, and reliable. But they're rigid — they always follow the same path. If an LLM doesn't know something, a chain can't decide to search the web or try a different approach. That's where agents come in (we'll see this in Day 5).

Day 2: Prompt Templates & Output Parsers

Reusable Prompts + Structured Outputs

Prompt Templates

A prompt template lets you write a prompt once with placeholders like {product_name} and reuse it with different values. Instead of hardcoding every detail, you create a template and inject variables at runtime.

Template Example: 
template = """You are a marketing expert.
Write a 2-sentence product description for: {product_name}
Target audience: {audience}"""

# Use multiple times
result1 = template.format(product_name="Laptop", audience="Developers")
result2 = template.format(product_name="Phone", audience="Students")

Output Parsers

By default, an LLM replies in free-flowing text — hard for code to use reliably. An output parser instructs the LLM to reply in a specific structure (like JSON) so your code can read fields directly.

Without Parser (Messy): 
response = "The product costs $99 and has 4.5 stars"
# How do you extract price? Regex? Fragile!
With JsonOutputParser (Clean): 
response = {"price": 99, "rating": 4.5}
price = response["price"]  # Easy!

Template → LLM → Parser Flow

Key Concepts

  • PromptTemplate: Create reusable prompts with variables
  • StrOutputParser: Returns response as plain text string
  • JsonOutputParser: Returns response as valid JSON object
  • Pydantic Models: Define expected output structure precisely
  • Structured Output: Data your code can reliably parse

Why This Matters

Parsers make your application reliable. Instead of hoping the LLM's response contains what you need, you enforce a contract: "reply with exactly these fields in this format."

Example: A customer service bot that extracts sentiment, urgency, and category from emails — without a parser, you'd spend time writing regex. With a parser, the LLM does it right.

Key Takeaway: Prompt templates make your code DRY (Don't Repeat Yourself). Output parsers make your code reliable. Together, they transform unstructured LLM responses into data your application can trust and use.

Day 3: Memory & Tool-Calling

Conversation Context & External Functions

Memory: Giving LLMs Context

By default, an LLM has no memory — each call is independent. It can't remember previous messages or refer to earlier parts of a conversation.

Without Memory: 
User: "My name is Ahmed"
Bot: "Nice to meet you, Ahmed!"

User: "What's my name?"
Bot: "I don't know, you didn't tell me" ❌
With Memory: 
memory = ConversationMemory()
# Keeps track of all messages
# Feeds them back into each new call
memory.add("User: My name is Ahmed")
memory.add("Bot: Nice to meet you, Ahmed!")

User: "What's my name?"
Bot: "Your name is Ahmed" ✓

Tool-Calling: Giving LLMs Actions

Tool-calling means giving the LLM access to functions it can choose to use — a calculator, a search engine, a database lookup. The LLM decides when to call a tool and what to pass into it.

Without Tools: 
User: "What's 2847 × 3956?"
LLM: "I think it's around 11 million" ❌
With Calculator Tool: 
Tools available: [calculator, search, database]
User: "What's 2847 × 3956?"
LLM: "I'll use the calculator tool"
Result: "11,270,632" ✓

How Tool-Calling Works (ReAct Loop)

Key Concepts

  • Conversation Memory: Stores chat history and feeds it back
  • Chat History: List of past user/assistant messages
  • Tool/Function Calling: LLM decides which tool to use
  • Tool Schema: Definition of a tool (name, description, parameters)
  • ReAct Loop: Reason → Act → Observe → Repeat

Real-World Example

Query: "What's the weather in Paris, and what should I wear?"

  1. LLM thinks: "I need current weather data"
  2. Calls weather tool → Gets "10°C, rainy"
  3. LLM thinks: "Now I have weather, I can answer"
  4. Final answer: "Bring an umbrella and a warm jacket"
Key Takeaway: Memory lets LLMs remember context. Tool-calling lets them take actions. Together, they transform a simple language model into an intelligent agent that can hold conversations and get real work done.

Day 4: What is LangGraph?

Building Decision-Making Systems

Chain vs. Agent (vs. Graph)

A chain is linear — always the same steps in the same order.

An agent is intelligent — it can decide what to do next based on the situation.

A graph is how we build these decision systems. It's a visual way to represent: nodes (steps), edges (connections), conditional edges (decisions), and state (data flowing through).

Core LangGraph Concepts

  • Node: A single step or function in the graph
  • Edge: A connection showing what happens next
  • Conditional Edge: A decision point ("if result is X, go to node Y")
  • State: The data passed along and updated as it moves
  • Graph: The entire system of nodes, edges, and state

Chain vs. Graph vs. Agent

Chain (Linear)

Always same order

Graph (Conditional)

Can branch based on logic

Agent (Dynamic)

Loops until solution found

Example: Order Status System (LangGraph)

Why LangGraph?

Chains are too simple — they can't handle "if this, then that" logic.

Agents are flexible but hard to visualize and debug.

LangGraph gives you a visual, structured way to build intelligent systems. You can see the flow, add branching logic, and know exactly what will happen.

State in LangGraph

State is the "data package" that flows through your graph. As it moves from node to node, each node can read the state and update it.

Example State: 
{
  "order_id": "ORD-12345",
  "status": "processing",
  "items": ["Laptop", "Mouse"],
  "customer": "Ahmed",
  "action_taken": None
}
Key Takeaway: LangGraph lets you build systems that can make decisions and follow different paths. It's perfect for workflows where "sometimes we do this, sometimes we do that" — like our upcoming orchestrator agent project.

Day 5: Orchestrator Agents

Multi-Agent Systems & Routing

What is an Orchestrator Agent?

An orchestrator agent receives a task, figures out what needs to happen, and routes it to the right specialized agent. It's like a manager — it doesn't do the work itself, it decides who should do it.

Analogy: 
Customer Task: "I need a report on Q3 sales"
├─ Orchestrator reads the task
├─ Thinks: "This is a sales question"
├─ Routes to → Sales Analysis Agent
└─ Collects result & returns to user

Multi-Agent Systems

Instead of one giant agent that can do everything, you have multiple specialized agents:

  • Sales Agent: Handles sales queries, revenue data
  • Support Agent: Handles customer support tickets
  • HR Agent: Handles hiring, benefits questions
  • Orchestrator: Decides which agent handles each task

Orchestrator Agent Flow

Real Example

User Query: "What's my Q3 revenue and do I have any pending support tickets?"

  1. Orchestrator receives the query
  2. Recognizes TWO subtasks: sales question + support question
  3. Routes to Sales Agent → gets revenue report
  4. Routes to Support Agent → gets pending tickets
  5. Combines both results
  6. Sends to user: "Your Q3 revenue was $500K. You have 3 pending tickets..."

Key Concepts

  • Orchestrator/Router Pattern: Central agent that routes tasks
  • Multi-Agent System: Multiple specialized agents working together
  • Shared State: Agents can pass information to each other
  • Supervisor Agent: Manages and coordinates agents
  • Task Decomposition: Breaking complex queries into subtasks

Why Our Next Project Needs Orchestrator Agents

The mini-project (Day 6) receives a raw retail CSV and must decide: clean first, then analyse, then visualise. Instead of one monolithic script, we build 4 specialised agents coordinated by an orchestrator.

  • Orchestrator Agent: Receives the raw CSV, decides the processing order, routes to each agent in sequence
  • Clean Agent: Fixes missing values, wrong data types, removes duplicates
  • Analysis Agent: Generates total sales, best-sellers, regional & category breakdowns
  • Visualization Agent (Bonus): Turns the analysis into bar, line, and pie charts

This design is modular, scalable, and much easier to debug. See the full agent specs in

Key Takeaway: Orchestrator agents turn messy, complex problems into organized workflows. They separate concerns (each agent handles one thing), make systems more maintainable, and are how real AI applications scale.

Day 6: The Project — Retail Data Pipeline

4 Agents · Real CSV Data · End-to-End Automation

What We're Building

A multi-agent LangGraph pipeline that takes a raw retail CSV file and automatically cleans it, analyses it, and produces a dashboard-ready summary — all coordinated by an orchestrator agent.

Input: Retail CSV Output: Insights + Charts LangChain + LangGraph

The 4-Agent Pipeline

Agent Specifications

01

Orchestrator Agent

Manager · Router · Coordinator

The orchestrator is the entry point. It receives the raw retail CSV, inspects it, and decides the correct processing sequence — always cleaning before analysing. It coordinates all other agents and collects their outputs into a final report.

Think of it as the project manager: it never does the actual work itself, it just makes sure the right agent handles each job in the right order.

Responsibilities

  • Receive: Raw retail CSV as input
  • Inspect: Understand what the data contains
  • Decide: Set processing order (Clean → Analyse → Visualise)
  • Route: Pass data to the correct agent at each step
  • Collect: Gather outputs from all agents
  • Return: Final aggregated result to the user
Orchestrator Logic (pseudo-code): 
def orchestrator(csv_path):
    state = {"raw_data": load_csv(csv_path)}

    # Always clean first
    state = clean_agent.run(state)

    # Then analyse the clean data
    state = analysis_agent.run(state)

    # Bonus: visualise if requested
    if state.get("visualize"):
        state = viz_agent.run(state)

    return state["final_report"]
02

Clean Agent

Data Cleaner · Validator · Transformer

Raw retail data is almost always messy — missing prices, wrong date formats, duplicate transactions, invalid category names. The Clean Agent handles all of this before any analysis happens. Garbage in, garbage out — this agent prevents that.

It receives the raw DataFrame from the orchestrator and outputs a cleaned, validated dataset ready for analysis.

Responsibilities

  • Missing Values: Fill or drop null entries in key columns
  • Data Types: Convert dates, prices, quantities to correct types
  • Duplicates: Remove identical or near-duplicate rows
  • Broken Rows: Drop rows with invalid/impossible values
  • Standardise: Normalise category names and region labels
  • Output: Return a clean DataFrame to the orchestrator
What the Clean Agent fixes: 
# Before cleaning (raw CSV issues):
# - "price" column has "$" symbols → not numeric
# - "date" is stored as "01/15/2024" string
# - 3% of rows have NaN in "quantity"
# - 12 duplicate transaction rows
# - "Electronics", "electronics", "ELECTRONICS" → inconsistent

# After Clean Agent:
# - price: float64  ✓
# - date: datetime64  ✓
# - quantity NaNs: filled with median  ✓
# - duplicates: removed  ✓
# - categories: lowercase, standardised  ✓
03

Analysis (EDA) Agent

Data Analyst · Insight Generator · Summariser

Once the data is clean, the Analysis Agent runs Exploratory Data Analysis (EDA) — it digs into the numbers and extracts the key business insights. It doesn't just compute statistics; it produces a structured, readable summary.

The output is a structured insights object (dictionary/JSON) that can feed a dashboard or be displayed directly to the user.

Insights Generated

  • Total Sales: Sum of revenue across all transactions
  • Best-Selling Products: Top N products by quantity and revenue
  • Sales by Region: Breakdown of revenue per geographic region
  • Sales by Category: Revenue split across product categories
  • Time Trends: Monthly or weekly sales trends
  • Summary Stats: Avg order value, total transactions, peak period
Analysis Agent output (structured): 
{
  "total_revenue": 847293.50,
  "total_transactions": 12841,
  "avg_order_value": 65.98,
  "top_products": [
    {"name": "Wireless Headphones", "revenue": 92400},
    {"name": "Laptop Stand",        "revenue": 78200}
  ],
  "sales_by_region": {
    "North": 312000, "South": 198000,
    "East":  201000, "West":  136293
  },
  "sales_by_category": {
    "Electronics": 420000,
    "Accessories":  230000,
    "Stationery":   197293
  },
  "peak_month": "November 2024"
}
04

Visualization Agent Bonus

Chart Builder · Dashboard Generator

After the Analysis Agent produces structured insights, the Visualization Agent turns that data into charts. It only runs once the first three agents are working reliably — treat it as a stretch goal.

It reads the analysis output and generates bar charts, line graphs, and pie charts using a library like Matplotlib or Plotly, saving them as image files or rendering them inline.

Charts to Generate

  • Bar Chart: Top products by revenue
  • Pie Chart: Sales split by category
  • Bar Chart: Revenue by region
  • Line Chart: Monthly sales trend over time
  • Output: Save as PNG files or display in notebook
Visualization Agent (pseudo-code): 
def viz_agent(state):
    insights = state["insights"]

    # Bar chart: top products
    plot_bar(insights["top_products"], title="Top Products by Revenue")

    # Pie chart: sales by category
    plot_pie(insights["sales_by_category"], title="Revenue by Category")

    # Line chart: monthly trend
    plot_line(insights["monthly_trend"], title="Sales Over Time")

    state["charts_saved"] = True
    return state

Recommended Build Order

1
Clean Agent first

Test it standalone with a sample CSV. Verify output is clean before touching anything else.

2
Analysis Agent second

Feed it the clean output from step 1. Check all insight fields are correct.

3
Orchestrator Agent third

Wire agents 1 and 2 together. Test the full pipeline end-to-end with the raw CSV.

4
Visualization Agent last (bonus)

Only add this once the first 3 agents work reliably end-to-end.

Key Takeaway: Build and test each agent in isolation before connecting them. The orchestrator is the last piece to wire up, not the first. This way, if something breaks, you know exactly which agent is responsible.
